# Repository instructions

- Write all documentation, code comments, diagnostic text and commit messages in English; documents contain no Han characters. Call this system `krepi` and the device casξ; use `casxi` where only ASCII is allowed, such as identifiers and paths.
- This repository owns the Rust/AArch64 microkernel, architecture and board support, the system ABI, the EL0 system services, runtime adapters and the SDK, integrated system tests, and the kernel's formal verification. CAS algorithms belong to kalyx, reusable UI and the graphical shell to kosmo, and language and proof engines to their own repositories.
- The repository is newly initialized. There is no source code, and commands such as `cargo xtask check`, `cargo xtask docs check` and `cargo xtask formal run` do not exist yet. They arrive with the change that pins the toolchain and adds the `xtask` skeleton. Until then, do not describe or run them as if they worked, and do not record their results.
- The hardware target is Raspberry Pi 5. Validate generic mechanisms on QEMU virt/Cortex-A76 first. Do not treat QEMU as a Pi 5 board model or reuse its addresses, interrupt routing or boot assumptions in Pi 5 board support.
- The microkernel keeps protection, scheduling, communication and essential interrupt mechanisms in EL1. Ordinary drivers, file systems, general executable loading and application policy belong in EL0. Internal object metadata alone does not provide hardware isolation or a scheduler. The kernel stays `no_std`.
- Build one image per supported board that serves every product function. Product profiles are never mutually exclusive at compile time; when two functions cannot yet run together, build a narrow slice of both inside the same image. The default image contains no diagnostic operations or fault probes, and diagnostic operation numbers are kept apart from production ones.
- SMP and application parallelism are required capabilities. Design every data structure for multiple CPUs even while it executes on one: classify per-CPU, per-thread, per-process and shared state, keep thread execution exclusive and budgets aggregated across CPUs, and synchronize cancellation, TLB invalidation and reclamation before enabling parallel access. Local IRQ masking, `volatile` and `UnsafeCell` do not provide cross-CPU synchronization.
- Before admitting non-cooperative applications, provide EL0 page permissions, timer preemption, bounded system calls, safe user-buffer access and complete context switching, and save all FP/SIMD state before enabling it for applications.
- Version external messages and use rights-bearing handles. Specify ownership, quotas, cancellation and asynchronous lifetimes. Do not expose internal Rust layouts or device pointers as an application ABI.
- Explain every unsafe operation's address, alignment, CPU-state, initialization or exclusivity requirements. Distinguish Rust safety, CPU access control and DMA isolation.
- Keep kernel paths bounded; IRQ and fatal-diagnostic paths must not allocate or borrow main-loop state.
- Treat kernel formal verification as a primary engineering objective and follow [formal verification](docs/formal-verification.md). Write a specification from the `requirements.md` and `contract.md` of its component below `docs/domains/` and from the feature documents, never from the implementation. Use Lean 4 + Charon/Aeneas for implementation refinement. Never edit generated Lean, weaken a statement, add an axiom or register a new trusted item without review; fix production defects against the intended contract and tool failures at the tool boundary.
- Code inside a proof target uses the provable Rust subset, the constructs that the pinned extraction tools translate, as a coding convention states it (planned).
- Every module taken from the prototype tree, a frozen earlier implementation that is not public, gets a porting record in the same change; follow [porting](docs/conventions/porting.md). Never modify the prototype tree.
- Only receipts produced by CI or by the hardware-in-the-loop bench, and stored where they can be retrieved, are acceptance evidence. Local runs are for development. Host tests, QEMU behaviour and hardware operation validate different properties; report each separately.
- Every Pi 5 result names the firmware, EEPROM and BL31 versions and the bench configuration from the firmware and lab registry (planned). A firmware or bench change requires the affected results to be obtained again.
- Tests do not depend on CPU speed, the wall clock or a fixed QEMU instruction count. Time slices, spin limits and timeouts are platform parameters. Follow [testing](docs/conventions/testing.md).
- Tests and tools are written in Rust. Do not add Python tooling.
- Follow the [documentation](docs/conventions/documentation.md) conventions. Milestone, task, proposal and decision numbers, capability and interface codes, and agent narratives belong in the project's coordination records outside this repository and appear in no document or code comment here; requirement IDs such as `IPC-R01` label requirements within a component and are not planning identifiers.
- Place generated outputs in the ignored `artifacts/` and `target/` directories. Once the toolchain is pinned, use `rust-toolchain.toml` and `Cargo.lock` as committed.
- Inspect Git status before editing and preserve unrelated changes. Use English Conventional Commit subjects of at most 72 characters and the local `.githooks/commit-msg` hook. Do not change global Git configuration, create remotes or publish without authorization.
